## Section 8: Observations and Recommendations

### 8.1 What Worked Well

- **Fail-closed lifecycle checks:** stage 30 tied tests, checks, review state, and head stability to exact SHAs before declaring either PR ready.
- **Review freshness checks:** stage 40 bound each accepted CCRA review to the intended head and required a newer review after remediation.
- **Useful agent specialization:** CCA produced both implementations, CCRA caught the only latent correctness issue, and the local shepherd handled validation and convergence.
- **Control isolation:** logs explicitly honored `LESSON_PROPAGATION=off`; no campaign-memory files were read or changed.
- **Strong throughput:** both serial tasks merged within a 36-minute campaign, with only three total review rounds.

### 8.2 What Could Improve

- **Boundary coverage:** [#2](https://github.com/edburns/dd-3068633-linux-x64-02/issues/2)'s six canonical tests did not cover the first value outside signed 64-bit Fibonacci range.
- **Token efficiency:** 1.99 million input tokens for two small PowerShell tasks is high. Repeated inclusion of long skill references, command bodies, and repository snapshots appears to dominate local context.
- **Phase gaps:** approximately 11m 26s of the campaign window was outside recorded Copilot sessions. Some is expected orchestration/bookkeeping, but it is not categorized in current artifacts.
- **Telemetry clarity:** token type labels are redacted, and hosted CCA/CCRA usage is unavailable, limiting end-to-end cost comparison.

### 8.3 Recommendations

1. Add explicit numeric-boundary tests around `Fibonacci(92)` and `Fibonacci(93)` to the issue template or canonical gate whenever accepted input exceeds fixed-width arithmetic.
2. Keep SHA-bound review freshness and second-review requirements; they directly prevented the overflow fix from merging without independent confirmation.
3. Emit a compact per-phase machine-readable summary containing start/end timestamps, PR, validated SHA, test count, review IDs, comment counts, remediation count, merge SHA, and outcome. This would eliminate report-time extraction from verbose transcripts.
4. Record orchestration transition timestamps so session gaps can be separated into GitHub wait time, process startup, and script overhead.
5. Reduce repeated prompt payload by referencing stable skill material once per session or loading only the required sections; compare token totals against a future treatment campaign before changing behavior.
6. Preserve `lessonPropagation` in all run metadata and post-mortems so this control run remains directly comparable with campaign-mode treatment runs.
